# Zitrange PRD

> 中文字体分包与优化工具 · v1.0
> 最后更新：2026-09-03

---

## 1. 背景与问题

### 1.1 问题

中文字体单字重 10–25MB，直接用于 Web 会导致首屏字体加载数十秒，或长时间 FOIT / 大段 FOUT。这是中文站点使用自定义字体最大的障碍。

### 1.2 现有方案的不足

| 方案 | 问题 |
|---|---|
| 直接上完整字体 | 10–25MB，首屏不可用 |
| 手动挑字做子集 | 内容一变就缺字，无法维护 |
| 在线切字网站 | 要上传字体（商业字体有授权风险）；多为一次性静态子集；不解决「内容动态变化」 |
| Google Fonts 式 CDN | 只有开源字体可选，不能用自己的商业字体 |

### 1.3 Zitrange 的定位

一个**本地运行**的桌面工具，把任意中文字体按 `unicode-range` 切成按需加载的分片，产出可直接上线的 woff2 + CSS。字体文件全程不出本机。

---

## 2. 目标与非目标

### 2.1 目标

- **G1** 把 10–25MB 中文字体切成按需加载分片，典型页面实际传输量降到 **200KB 以内**
- **G2** 支持批量处理：一次任务处理多字重家族（zip / 文件夹，常见 100–300MB 打包）
- **G3** 提供可验证的收益预览：处理前就能预测「这个页面会下载哪些片、多少 KB」
- **G4** 零配置启动，字体不出本机
- **G5** 架构上可平滑演进为独立桌面应用（Tauri），UI 零改动

### 2.2 非目标（v1 明确不做）

- **N1** 不做字体轮廓编辑 / 造字 / 改字形
- **N2** 不做云端部署与多租户（架构预留，v1 不实现）
- **N3** 不做 URL 抓取的 SPA 渲染（需 headless 浏览器，成本过高）；v1 仅抓静态 HTML
- **N4** 不做字体授权校验与管理（仅在使用协议中提示用户自行确认授权）
- **N5** 不做 CDN 上传
- **N6** 首版不做可变字体 instancing（见 §11 开放问题 O2）

## 3. 目标用户与场景

### 3.1 主要用户

- **前端工程师**：给公司站点接入品牌中文字体，需要可控、可复现、可进构建流程
- **独立开发者**：个人站点 / 博客想用好看的中文字体，但被体积劝退
- **设计师转前端**：有设计稿和字体文件，需要产出可直接交付开发的产物

### 3.2 核心场景

**S1 · 内容固定型站点（企业官网、落地页、活动页）**
文案基本不变。扫描站点现有文案 → 只打包用到的字 → 体积极小，且可精确预测。

**S2 · 内容动态型站点（博客、CMS、UGC）**
内容不可预知。用内置字频表切分兜底，按频率排序分片，保证任意内容都能命中且优先加载高频片。

**S3 · 混合**
以站点用字保证核心页面最优，叠加字频分块兜底生僻字，兼顾两者。

## 4. 核心概念

| 概念 | 定义 |
|---|---|
| **字符集（Charset）** | 本次任务需要覆盖的 Unicode 码位集合 |
| **分片（Chunk）** | 字符集的一个子集，产出一个 woff2 文件 + 一条 `@font-face` |
| **拆分方案（Partition）** | 字符集 → 分片列表的映射结果 |
| **任务（Job）** | N 个字体文件 × 1 套拆分方案 = 1 个任务 |
| **覆盖率（Coverage）** | 字符集中能在源字体里找到字形的码位占比 |
| **缺字（Missing）** | 在字符集中、但源字体里没有字形的码位 |

**架构上的核心抽象**：引擎只做「给定一组码位 → 输出一个 woff2」这一件事；所有策略差异都收敛为「如何把字符集分组」。这个抽象让三种拆分策略可以共存，也让测试变得简单。

## 6. 核心算法设计

### 6.1 字符集提取

从文本/文件中提取码位：

1. 按 UTF-8 解码，逐码位收集
2. 保留：CJK 统一表意文字及扩展区（U+4E00–9FFF, U+3400–4DBF, U+20000–2FA1F, U+30000–323AF）、CJK 标点（U+3000–303F）、全角字符（U+FF00–FFEF）、拉丁字母数字、ASCII 标点
3. 排除：ASCII 控制字符、Unicode 私用区、以及（可选）源码文件中的标识符与注释
4. 输出：`Map<codepoint, count>`，并做频率降序排序

### 6.2 Unicode 频率表（内置资产）

需要一份按使用频率降序的汉字表，作为字频分块策略的核心资产。

- 数据量：约 10,000 字，降序排列
- 候选来源：《通用规范汉字表》一级 3500 字（本身即按频率排序）+ 现代汉语常用字表 + 公开语料字频统计
- 交付形式：`packages/core/assets/charfreq-zh.json`
- 许可证：使用公开字表数据，**必须在代码中注明数据来源与授权**，不可使用来源不明的商业字库数据
- 覆盖率参考：前 200 字 ≈ 覆盖中文文本 50%；前 1000 字 ≈ 90%；前 3500 字 ≈ 99.5%

#### 6.2.1 字符集构建：模式 × 字源 × 兜底

步骤 02「你的网站会出现哪些字」提供**字源**，步骤 03「分片模式」提供**怎么用这份字源**的策略。三者——字源 `S`、模式 `M`、兜底字表 `T`——共同决定最终有序字符集 `C`，再交给 §6.3 分片。

**输入定义**
- **字源 `S`**：步骤 02 粘贴/上传的文本与文件，提取为 `Map<cp, count>`（实际频次），可能为空。
- **兜底字表 `T`**：步骤 03「兜底字表」所选档位对应的全局字频降序码位表（`none` / `common-3500` / `common-7000` / `gb2312` 全集）。
- **ASCII 保底 `A`**：数字/字母/常用标点（F2.4），仅当源字体支持且尚未包含时并入，所有模式一致。

**三种模式的构建规则**

| 模式 | 字符集 | 排序 | 与步骤 02 的关联 | 兜底约束 |
|------|--------|------|------------------|----------|
| **站点** site | 仅 `S` | 按 `S` 实际频次降序 | 02 是唯一来源；02 为空则字符集仅含 `A`（需告警） | 强制 `none`，UI 禁用兜底下拉 |
| **混合** hybrid（默认） | `S ∪ T` | `S` 的字符按实际频次降序在前；`T\S` 的字符按全局字频表降序在后 | 02 决定核心页面用字与排序，兜底只补全生僻字 | 尊重用户选择（默认 `common-3500`） |
| **字频** frequency | `S ∪ T` | 全部按全局字频表降序，**忽略 `S` 的实际频次** | 02 仅作保底包含，不改变排序；面向内容不可预知 | 必须非 `none`，否则无字符集（需告警） |

**实现要点**
- `rank(cp)` = 码位在全局字频表中的名次（越小越高频）；不在表中的字赋极大 rank，排最后。
- 站点与混合模式下，站点字符的相对次序一律按其**实际频次**（站点自身的高频字进更小的优先片）；兜底字符按其 `rank(cp)`。
- 字频模式下，连站点字符也按 `rank(cp)` 重排——这正是「内容不可预知时按通用频率优化」的含义。
- ASCII 保底 `A` 在所有模式末尾统一并入（F2.4 单独成第 0 片）。

**UI 约束（模式 ↔ 兜底 联动）**
- 切到「站点」：兜底字表自动置为 `none` 并禁用，避免与「只用扫描到的字」自相矛盾。
- 切到「字频」：兜底字表不可为 `none`；若为 `none` 在 §6.7 校验里告警。
- 切到「混合」：兜底字表自由。

> 三种模式已由 `processFont` 按本表规则构建字符集（O7 已实现）。自动分片之后，用户还可在 §6.3.1 用 `strategy.overrides` 做手动微调（合并 / 拆分 / 钉字 / 排除）。

### 6.3 分片算法

```
输入：有序字符集 C（构建规则见 §6.2.1，已按对应模式排好序）、参数 { baseSize, growth, fallbackSet }
输出：分片列表

1. ASCII + 常用标点单独成 chunk[0]
2. 剩余字符按频率降序排列
3. 若启用递增分片（F2.5）：
     第 k 片大小 = baseSize × growth^k，并 clamp 到 [baseSize, maxSize]
     （默认 baseSize=200, growth=1.35, maxSize=800）
   否则：每片固定 baseSize
4. 依次切分，最后一片余数若 < baseSize/3 则并入前一片
```

**递增分片的依据**：高频片几乎必然被加载，切小一点能让首屏下载更快；低频片很少被加载，切大一点能减少请求数和固定开销占比。

**固定开销约束**（决定分片不能太小）：每片 woff2 都带一份完整的表结构（cmap/hmtx/head/hhea/maxp/name/OS2/post），约 2–5KB。

| 单片字数 | glyf 数据（woff2 后） | 固定开销占比 |
|---|---|---|
| 50 字 | ~9KB | ~35% ❌ 浪费明显 |
| 200 字 | ~35KB | ~12% ✅ 甜点区 |
| 800 字 | ~140KB | ~3% ✅ |

### 6.3.1 分片手动编辑（F2.11）

自动分片给出「合理但通用」的结果；手动编辑让用户在自动结果之上做微调，对应 PRD F2.11。引擎侧由 `partition.applyOverrides` 实现，支持四种操作：

| 操作 | `kind` | 作用 |
|------|--------|------|
| 合并片 | `merge` | 把第 `a`、`b` 片合并为一片（`a`、`b` 为相邻索引） |
| 拆分片 | `split` | 把第 `chunk` 片从 `at`（默认中位 `median`，或指定位置）拆成两片 |
| 钉字 | `pin` | 把指定字符从其他片抽出，钉入第 `to` 片片首（该片一旦加载这些字必可用） |
| 排除 | `exclude` | 把指定字符从所有片中移除（用于彻底不想要的字） |

**叠加语义**：`overrides` 是一个有序列表，按顺序作用在「自动分片结果」之上，存入 `strategy.overrides`。每次用户操作都基于**当前可见分片**追加一条 override，因此索引始终指向「前序 overrides 应用后的当前分片数组」，追加式叠加天然一致——即便此前已合并/拆分过，新操作引用的仍是屏幕上看到的那片。

**与参数调整的关系**：调整 `baseSize / growth / maxSize / 模式 / 兜底` 后重新生成，自动分片会变化，但 `overrides` 仍叠加在其上。即「手动编辑 = 在自动策略之上的微调」，而非替代自动策略。若自动分片已不含被引用的片，对应 override 自动跳过（不报错）。

**UI 落点（v1）**：`ChunkTable` 分片清单内——
- 每片行内：「合并↓」（与下一片合并，末片禁用）、「拆分」（从中位拆两片）；
- 表格底部：「钉字」（输入字符 + 选择目标片）、「排除」（输入字符全局移除）、「重置手动编辑」（清空 `overrides`）。
- 拖拽式逐字编辑不在 v1 范围（见 O6）。

### 6.4 `unicode-range` 生成

1. 分片内码位排序
2. 合并连续码位为区间：`[4E00, 4E01, 4E02]` → `U+4E00-4E02`
3. 孤立码位保留单值
4. 逗号连接输出

**关于通配符（`U+4E??`）**：通配符会声明字体里可能不存在的码位。浏览器下载该片后找不到字形，会回退到下一个 font，造成同段落内字体不一致——这是正确性问题，不是性能问题。

因此规则：**仅当某 256 对齐块被完整包含时才允许使用通配符；默认关闭，仅作为可选优化且需强制校验。**

### 6.5 按需加载模拟（F4.3，核心差异化功能）

这是整个工具最有说服力的功能——让用户在处理之前就看到收益。

```
输入：样本文本 T
1. 提取 T 的码位集合 S
2. 遍历分片列表，标记命中：chunk ∩ S ≠ ∅
3. 模拟传输量 = Σ 命中分片的文件大小
4. 输出：命中片清单（编号 + 大小）+ 总传输量 + 命中率
```

同时给出三个数字的对比：

```
源字体        12.4 MB
全部分片合计   780 KB   （压缩率 94%）
本页实际加载   96 KB    （命中 4/18 片）
```

注意关键认知：浏览器**只会下载用到的分片**，"全部分片合计"只是磁盘成本，不是首屏成本。工具必须把这个区别讲清楚，否则用户会误判。

### 6.6 智能参数建议（F2.8）

设计原则：**可解释，非黑箱**。用户是开发者，必须说清"为什么这么建议"，而不是丢一个数字。

```ts
interface Recommendation {
  strategy: PartitionStrategy;
  format: OutputFormat[];
  reasons: Reason[];
  estimate: { chunkCount: number; totalSize: number; typicalPageLoad: number };
}

interface Reason {
  id: string;                       // R1..R7，便于前端做「忽略此建议」
  level: 'info' | 'warn';
  text: string;                     // 人话：为什么这么建议
  evidence: string;                 // 数据：依据的实测值
}
```

按顺序匹配，命中即采用：

| 规则 | 触发条件 | 建议 | 理由 |
|---|---|---|---|
| **R1** | 字符集 ≤ 500 字 | 单片不切分 | 每片固定开销 3–5KB，切分后总量反而变大 |
| **R2** | 500 < n ≤ 3000，且站点用字占比 > 0.7 | 站点用字模式，2–4 片，每片 ~600 字 | 字符少且集中，少量大片即可覆盖，减少请求数 |
| **R3** | n > 3000，或启用了兜底字表 | 混合模式 + 递增分片（base 200 / growth 1.35 / max 800） | 高频字集中在少数片，递增让首屏只下载小片 |
| **R4** | 字符来源全部为内置字表（无站点文本） | 字频分块模式 | 无站点特征，只能按通用频率优化 |
| **R5** | 源字体 > 15MB 且字符集 < 2000 | 追加提示：可继续收紧字符集 | 压缩比已接近极限，进一步优化空间在字符集本身 |
| **R6** | 输出格式 | 默认 `woff2`；勾选「需兼容 IE11 / 老 Safari」时追加 `woff` | 见 §6.8 |
| **R7** | 命中 R2/R3 且用户已给出样本文本 | 用样本文本跑一次模拟，把"预计首屏加载量"写进理由 | 让建议直接带上可感知的收益数字 |

UI 行为：分析完成后参数面板预填推荐值，旁边列出命中的规则（含 evidence 数字）。用户可任意覆盖；被覆盖的项标记为「已修改」，支持一键还原。

### 6.7 自定义实时校验（F2.9）

用户改参数时即时提示，**不阻止、只提示**——这是建议与自定义的闭环：自定义不是放任，而是带反馈的调整。

| 校验 | 触发 | 提示文案 |
|---|---|---|
| 单片过小 | `baseSize` < 100 | 固定开销占比约 >25%，建议 ≥ 150 |
| 单片过大 | `baseSize` > 2000 | 按需加载收益下降，单片将超过 ~500KB |
| 分片过多 | 分片数 > 50 | 请求数过多，可能受同域并发限制影响 |
| 覆盖率不足 | coverage < 95% | 列出缺字总数与前 20 个缺字 |
| 尾片过小 | 最后一片 < `baseSize`/3 | 建议并入前一片（提供一键操作） |
| 兜底过大 | 启用 GB2312 兜底但字符集 < 1000 | 兜底将使体积增加约 N 倍，确认？ |

### 6.8 输出格式（F3.10）

**默认 `woff2`。**

| 格式 | 体积（相对源 TTF） | 浏览器支持 | 建议场景 |
|---|---|---|---|
| **woff2** | 40–60% | Chrome 36+ / Safari 10+ / Firefox 39+ / Edge 14+，约 97% | **默认，绝大多数场景** |
| woff | 50–70% | IE9+ / Safari 5.1+ | 需兼容 IE11 或老 Safari |
| ttf | 无压缩 | 全支持 | 非 Web 场景：原生 App、PDF 内嵌、设计软件 |

三条约束：

1. **不做轮廓类型转换。** 源字体是 CFF（`.otf`）就输出 CFF-flavored woff2，是 glyf（`.ttf`）就输出 glyf-flavored woff2。CFF ↔ glyf 互转需要 cu2qu 之类的转换工具，会改变字形质量，v1 不支持。UI 需注明「输出保持源字体的轮廓类型」。
2. **woff 无额外依赖。** fonttools 处理 woff 用标准库 zlib，不需要 brotli 之外的东西。
3. **多格式输出时**（F3.11），CSS 按优先级排列 `format()` 提示，浏览器自动取第一个支持的：

```css
src: url("fonts/MyFont-0.woff2") format("woff2"),
     url("fonts/MyFont-0.woff")  format("woff");
```

## 7. 技术架构

### 7.1 形态决策

采用**本地 Web 服务**：Vite + React 前端 + Node API 服务 + Python 字体处理子进程。

选型依据（完整的三方案评估见附录 A）：

- 字体处理必须跑原生进程。纯前端 WASM 方案受 32 位地址空间限制（堆上限约 2GB，且**只增不减**），10MB 字体峰值已达 ~1GB，批处理多字重时必然 OOM
- 本地服务开发调试最快，且保留了演进为云端服务的可能
- 相比 Tauri，绕开了「把 Python fonttools 打进 app bundle」这个麻烦环节，也不需要 Xcode / Rust 工具链与签名公证

### 7.3 关键接口

```ts
// src/adapters/types.ts —— A/C 方案唯一的差异点
export interface EngineClient {
  inspect(file: FileRef): Promise<FontInfo>;
  runJob(req: JobRequest, onProgress: (p: JobProgress) => void): Promise<JobResult>;
  cancelJob(jobId: string): Promise<void>;

**智能建议与参数校验不走服务端**（§6.6 / §6.7）。二者只依赖字符集统计与 inspect 返回的元数据，在 `src/core/` 内以纯函数实现、前端实时计算，参数面板每次改动都能得到毫秒级反馈。

// src/server/routes/jobs.ts
export interface JobRequest {
  fonts: FontInput[];         // 1..N 个字体文件（zip 已展开）
  sources: CharSource[];      // text | files | url | builtin
  strategy: {
    mode: 'site' | 'frequency' | 'hybrid';
    baseSize: number;         // 默认 200
    growth: number;           // 默认 1.35，1 = 关闭递增
    maxSize: number;          // 默认 800
    fallback: 'none' | 'common-3500' | 'common-7000' | 'gb2312';
    overrides?: ManualOverride[];  // F2.11 手动编辑，作用于自动分片结果之上
  };
  options: {
    format: OutputFormat[];   // F3.10 默认 woff2；F3.11 支持多选
    fontDisplay: 'swap' | 'block' | 'fallback' | 'optional';
    keepLayoutFeatures: boolean;   // 默认 true
  };
}

export type OutputFormat = 'woff2' | 'woff' | 'ttf';

// F2.11 分片手动编辑，按顺序作用在自动分片结果之上
export type ManualOverride =
  | { kind: 'merge';   chunks: [number, number] }
  | { kind: 'split';   chunk: number; at: 'median' | number }
  | { kind: 'pin';     chars: string[]; to: number }
  | { kind: 'exclude'; chars: string[] };

export interface JobResult {
  groups: Array<{
    fontName: string;
    weight: number;
    style: 'normal' | 'italic';
    chunks: Array<{
      fileName: string;
      size: number;
      charCount: number;
      unicodeRange: string;
    }>;
  }>;
  report: {
    originalSize: number;
    totalSize: number;
    coverage: number;
    missingChars: string[];
  };
}
```

### 7.4 两阶段子集化（F3.8，性能优化）

**问题**：`pyftsubset` 每次调用都要重新解析整个源字体。10MB 字体解析约 5–10s。7 字重 × 20 分片 = 140 次调用 = 重复解析 140 次。

**方案**：

```
阶段一：源字体 (12MB) --pyftsubset--> 中间 TTF (含全部 3000 目标字符，约 1MB)
阶段二：中间 TTF --×20--> 20 个分片 woff2（每次解析 1MB，极快）
```

解析成本从「140 × 重」降为「7 × 重 + 140 × 轻」。

注意：阶段一必须保留全部布局特性（`--layout-features=*`），否则阶段二无法还原。且阶段二输出的 woff2 仍需复用阶段一的 cmap/GSUB/GPOS 语义。

**v1 可先实现单阶段（简单、正确性优先），但 `engine/subset.ts` 的接口设计必须允许后续替换为两阶段。**

## 8. A 方案（Tauri）扩展设计

v1 只做接口定义与目录预留，不实现。但架构必须保证后续改造成本可控。

### 8.1 隔离点

UI 层只依赖 `EngineClient` 接口（§7.3），不感知传输方式。

```
C 方案：web/ → httpAdapter  → fetch(/api)  → Node server → Python
A 方案：web/ → tauriAdapter → invoke(cmd)  → Rust sidecar → Python
```

改造工作量：**新增 `tauriAdapter.ts` + Rust 侧 command 桥接，UI 零改动。**

### 8.2 需要额外解决的三件事

| 事项 | 说明 | 预估难度 |
|---|---|---|
| **Python 依赖分发** | 不能要求终端用户装 Python。方案：PyInstaller 打包 fonttools 为独立二进制（约 30–40MB），或改用 Rust 原生子集化库 | 高 |
| **Sidecar 打包** | Tauri externalBin 配置、路径解析、进程生命周期 | 中 |
| **签名与公证** | macOS 需 Developer ID 签名 + notarization，否则 Gatekeeper 拦截 | 中 |
| **Rust 工具链** | 需 Xcode Command Line Tools + Rust，构建时间显著变长 | 中 |

### 8.3 触发时机

满足以下任一条件时启动 A 方案改造：

- 需要分发给不懂命令行的设计师 / 客户
- 用户反馈「装 Python 太麻烦」成为主要流失点
- 需要完全离线的一键安装包

在此之前保持 C 方案，把精力投入在拆分策略与预览体验上（这才是产品的真正难点）。

**字体文件体积的事实基线**（用于容量规划）：

- 单字重中文字体 TTF/OTF 集中在 **10–25MB**，物理上限约 40–60MB（CJK 全部码位约 9.8 万 × 每字形 200–500 字节）
- woff2 约为 TTF 的 40–60%
- **「几百 MB」通常不是单个文件，而是多字重家族压缩包**（7 字重 × 15MB ≈ 100MB）。因此核心需求是**批处理**，不是超大单文件处理
- 输入若为 woff2，需先 Brotli 解码重建 glyf，内存峰值比同内容 TTF 更高
