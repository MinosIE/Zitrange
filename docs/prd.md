# Zitrange PRD

> 中文字体分包与优化工具 · v1.0
> 最后更新：2026-09-04

---

## 1. 背景与问题

### 1.1 问题

中文字体单字重 10–25MB，直接用于 Web 会导致首屏字体加载数十秒，或长时间 FOIT / 大段 FOUT。这是中文站点使用自定义字体最大的障碍。

### 1.2 现有方案的不足

| 方案 | 问题 |
|---|---|
| 直接上完整字体 | 10–25MB，首屏不可用 |
| 手动挑字做子集 | 内容一变就缺字，无法维护 |
| 在线切字网站 | 要上传字体（商业字体有授权风险）；多为一次性静态子集；不解决「内容动态变化」 |
| Google Fonts 式 CDN | 只有开源字体可选，不能用自己的商业字体 |

### 1.3 Zitrange 的定位

一个**本地运行**的桌面工具，把任意中文字体按 `unicode-range` 切成按需加载的分片，产出可直接上线的 woff2 + CSS。字体文件全程不出本机。

---

## 2. 目标与非目标

### 2.1 目标

- **G1** 把 10–25MB 中文字体切成按需加载分片，典型页面实际传输量降到 **200KB 以内**
- **G2** 支持批量处理：一次任务处理多字重家族（zip / 文件夹，常见 100–300MB 打包）
- **G3** 提供可验证的收益预览：处理前就能预测「这个页面会下载哪些片、多少 KB」
- **G4** 零配置启动，字体不出本机
- **G5** 架构上可平滑演进为独立桌面应用（Tauri），UI 零改动

### 2.2 非目标（v1 明确不做）

- **N1** 不做字体轮廓编辑 / 造字 / 改字形
- **N2** 不做云端部署与多租户（架构预留，v1 不实现）
- **N3** 不做 URL 抓取的 SPA 渲染（需 headless 浏览器，成本过高）；v1 仅抓静态 HTML
- **N4** 不做字体授权校验与管理（仅在使用协议中提示用户自行确认授权）
- **N5** 不做 CDN 上传
- **N6** 首版不做可变字体 instancing（见 §11 开放问题 O2）

## 3. 目标用户与场景

### 3.1 主要用户

- **前端工程师**：给公司站点接入品牌中文字体，需要可控、可复现、可进构建流程
- **独立开发者**：个人站点 / 博客想用好看的中文字体，但被体积劝退
- **设计师转前端**：有设计稿和字体文件，需要产出可直接交付开发的产物

### 3.2 核心场景

**S1 · 内容固定型站点（企业官网、落地页、活动页）**
文案基本不变。扫描站点现有文案 → 只打包用到的字 → 体积极小，且可精确预测。

**S2 · 内容动态型站点（博客、CMS、UGC）**
内容不可预知。用「补全常用字」兜底，按码位均匀切片，保证任意内容都能命中（不依赖频率排序，分片模型见 §6.3）。

**S3 · 混合**
以站点用字为核心，叠加「补全常用字」兜底，兼顾两者——分片仍走同一套按码位均匀切片。

## 4. 核心概念

| 概念 | 定义 |
|---|---|
| **字符集（Charset）** | 本次任务需要覆盖的 Unicode 码位集合 |
| **分片（Chunk）** | 字符集的一个子集，产出一个 woff2 文件 + 一条 `@font-face` |
| **拆分方案（Partition）** | 字符集 → 分片列表的映射结果 |
| **任务（Job）** | N 个字体文件 × 1 套拆分方案 = 1 个任务 |
| **覆盖率（Coverage）** | 字符集中能在源字体里找到字形的码位占比 |
| **缺字（Missing）** | 在字符集中、但源字体里没有字形的码位 |

**架构上的核心抽象**：引擎只做「给定一组码位 → 输出一个 woff2」这一件事；所有策略差异都收敛为「如何把字符集分组」。这个抽象让分片保持单一且可单测——所有界面旋钮最终都只改变「字符集如何分组」。

## 6. 核心算法设计

### 6.1 字符集提取

从文本/文件中提取码位：

1. 按 UTF-8 解码，逐码位收集
2. 保留：CJK 统一表意文字及扩展区（U+4E00–9FFF, U+3400–4DBF, U+20000–2FA1F, U+30000–323AF）、CJK 标点（U+3000–303F）、全角字符（U+FF00–FFEF）、拉丁字母数字、ASCII 标点
3. 排除：ASCII 控制字符、Unicode 私用区、以及（可选）源码文件中的标识符与注释
4. 输出：`Map<codepoint, count>`（顺序无关，分片时按码位重排）

### 6.2 Unicode 频率表（内置资产）

需要一份按使用频率降序的汉字表，作为「补全常用字」兜底的字源（仅用于兜底包含，不参与分片排序）。

- 数据量：约 10,000 字，降序排列
- 候选来源：《通用规范汉字表》一级 3500 字（本身即按频率排序）+ 现代汉语常用字表 + 公开语料字频统计
- 交付形式：`packages/core/assets/charfreq-zh.json`
- 许可证：使用公开字表数据，**必须在代码中注明数据来源与授权**，不可使用来源不明的商业字库数据
- 覆盖率参考：前 200 字 ≈ 覆盖中文文本 50%；前 1000 字 ≈ 90%；前 3500 字 ≈ 99.5%

#### 6.2.1 字符集构建：字源 × 兜底 × ASCII 保底

步骤 02「你的网站会出现哪些字」提供**字源**，步骤 03「分片策略」提供**兜底 / ASCII 保底**与**每片字数**等参数。三者——字源 `S`、兜底字表 `T`、ASCII 保底 `A`——共同决定最终字符集 `C`，再交给 §6.3 按码位均匀分片。

**输入定义**
- **字源 `S`**：步骤 02 粘贴/上传的文本与文件，提取为 `Map<cp, count>`（实际频次仅用于「是否包含该字」，不参与排序），可能为空。
- **拆分全量字体**：`useFontCmap=true` 时直接纳入字体 cmap 的全部码位，绕过兜底/保底上限——字符集即整本字形。
- **兜底字表 `T`**：仅「仅用户内容」模式生效（全量模式忽略）。档位 `none`（只切输入）/ `common`（补全通用常用字表前 3500 字）。
- **ASCII 保底 `A`**：数字/字母/常用标点（F2.4），仅当源字体支持且尚未包含时并入；可由 `includeAsciiPunct` 关闭。

**构建顺序（`processFont` 实现）**
1. 由字源 `S` 得到初始字符集（频次图，key 为码位）；
2. 全量模式：并入 cmap 全部码位；否则按所选 `T` 用 §6.2 字频表补全前 N 字；
3. ASCII 保底 `A` 并入（受字体支持裁剪）；
4. 顺序无关，交给 §6.3——分片内部按码位重排，不做任何频率排序。

> 分片模型已收敛为单一「按码位均匀切片」，`normalizeStrategy` 仅负责补齐默认值与约束兜底取值（见 §7.3），不再有模式分支。

### 6.3 分片算法（按码位均匀切片）

```
输入：字符集 C（构建见 §6.2.1；顺序无关，算法内部按码位重排）、参数 { baseSize, asciiFirst }
输出：分片列表

1. ASCII/标点单独成 chunk[0]（basic 片，开启 asciiFirst 时）；本身已是连续块，range 极短
2. 剩余字符按码位升序排序
3. 拆成极大连续段（步长 > 1 即断开）
4. 把连续段按固定每片字数 baseSize 装进定长片（bin-packing）：
   - 连续段本身不被拆散；只有超过 baseSize 的超长连续段才切片成连续子段
   - 因此连续子集里每片仍是单区间，单行 `unicode-range` 显著变短
   - 片数 = ⌈N / baseSize⌉，由每片字数直接控制
5. 若片数 > maxChunks（默认 512，内部安全上限，界面不暴露），顺序合并相邻段以控制 @font-face 数量
   （极端情况下合并后的片 range 会变长，属可接受退化）
```

**为什么能缩短 `unicode-range`**：每片内部码位连续，`toUnicodeRange`（§6.4）会把它们合并成极少数区间。典型场景是全量字体——cmap 多为 `4E00–9FFF` 这类巨型连续块，整块可折叠成 `U+4E00-9FFF` 单区间，单行 `unicode-range` 极短。

**代价**：放弃「高频字进小首屏片」的频率局域性，F4.3 首屏按需加载收益由 ASCII 首屏片（必然命中）与均匀码位切分共同决定。对字字分散的少量字符集收益有限（见 §6.4）。

**固定开销约束**（决定分片不能太小）：每片 woff2 都带一份完整的表结构（cmap/hmtx/head/hhea/maxp/name/OS2/post），约 2–5KB。

| 单片字数 | glyf 数据（woff2 后） | 固定开销占比 |
|---|---|---|
| 50 字 | ~9KB | ~35% ❌ 浪费明显 |
| 200 字 | ~35KB | ~12% ✅ 甜点区 |
| 4000 字 | ~700KB | ~0.5% ✅（默认档） |
| 8000 字 | ~1.4MB | ~0.2% ✅（粗切档） |

### 6.3.1 ~~分片手动编辑（F2.11）~~ **已移除**

> **已决定移除，不再实现。** 原计划暴露「钉字 / 排除」两类手动微调（引擎侧 `partition.applyOverrides`），
> 实际使用中「只用输入内容 + 调参数重新生成」已能满足诉求，手动编辑反而让 `ChunkTable` 与
> `PartitionStrategy` 长期背着一个少数场景才用的叠加层，故整条链路删除：
> `ManualOverride` 类型、`PartitionStrategy.overrides`、`applyOverrides` / `flattenChars`、
> 以及 `ChunkTable` 的「钉到片 / 排除 / 重置手动编辑」UI。分片清单保留逐片下载与「下载全部」。

### 6.4 `unicode-range` 生成

1. 分片内码位排序
2. 合并连续码位为区间：`[4E00, 4E01, 4E02]` → `U+4E00-4E02`
3. 孤立码位保留单值
4. 逗号连接输出

**关于通配符（`U+4E??`）**：通配符会声明字体里可能不存在的码位。浏览器下载该片后找不到字形，会回退到下一个 font，造成同段落内字体不一致——这是正确性问题，不是性能问题。

因此规则：**仅当某 256 对齐块被完整包含时才允许使用通配符；默认关闭，仅作为可选优化且需强制校验。**

**关于 `unicode-range` 长度的来源**：单行 `range` 的长度 = 该片的「连续段数量」。本工具按码位升序装箱，相邻字天然聚到同片、制造连续段，故单行较短。但需注意：**若字符集本身字字分散（几乎无连续段，如少量零散中文），则任何分片方式都无法在不声明不存在码位的前提下缩短 `range`**——此时唯一进一步压缩的手段是 §6.4 前述「整 256 块被完整包含时的通配符」（默认关，因正确性约束）。码位聚类对此类子集增益有限，其价值主要体现在全量字体（连续块多）场景。

### 6.5 按需加载模拟（F4.3，核心差异化功能）

这是整个工具最有说服力的功能——让用户在处理之前就看到收益。

```
输入：样本文本 T
1. 提取 T 的码位集合 S
2. 遍历分片列表，标记命中：chunk ∩ S ≠ ∅
3. 模拟传输量 = Σ 命中分片的文件大小
4. 输出：命中片清单（编号 + 大小）+ 总传输量 + 命中率
```

同时给出三个数字的对比：

```
源字体        12.4 MB
全部分片合计   780 KB   （压缩率 94%）
本页实际加载   96 KB    （命中 4/18 片）
```

注意关键认知：浏览器**只会下载用到的分片**，"全部分片合计"只是磁盘成本，不是首屏成本。工具必须把这个区别讲清楚，否则用户会误判。

### 6.7 自定义实时校验（F2.9）

用户改参数时即时提示，**不阻止、只提示**——这是参数校验与自定义的闭环：自定义不是放任，而是带反馈的调整。

| 校验 | 触发 | 提示文案 | 实现 |
|---|---|---|---|
| 字符集为空 | `charCount` = 0 且非全量模式 | 不会生成任何分片，请先提供文本 / 文件 / URL | E_EMPTY |
| 每片字数非法 | `baseSize` < 1 | 每片字数必须 ≥ 1 | E_BASE |
| 未选格式 | `format` 为空 | 未选择任何输出格式 | E_FMT |
| 仅输出 TTF | 含 `ttf` 不含 `woff2` | 体积大且无法利用分片缓存，建议至少保留 woff2 | W_TTF |
| 字符集超字形 | `charCount` > 字体字形数 且非全量 | 部分字符将缺字回退到其他字体 | W_MISS |

### 6.8 输出格式（F3.10）

**默认 `woff2`。**

| 格式 | 体积（相对源 TTF） | 浏览器支持 | 建议场景 |
|---|---|---|---|
| **woff2** | 40–60% | Chrome 36+ / Safari 10+ / Firefox 39+ / Edge 14+，约 97% | **默认，绝大多数场景** |
| woff | 50–70% | IE9+ / Safari 5.1+ | 需兼容 IE11 或老 Safari |
| ttf | 无压缩 | 全支持 | 非 Web 场景：原生 App、PDF 内嵌、设计软件 |

三条约束：

1. **不做轮廓类型转换。** 源字体是 CFF（`.otf`）就输出 CFF-flavored woff2，是 glyf（`.ttf`）就输出 glyf-flavored woff2。CFF ↔ glyf 互转需要 cu2qu 之类的转换工具，会改变字形质量，v1 不支持。UI 需注明「输出保持源字体的轮廓类型」。
2. **woff 无额外依赖。** fonttools 处理 woff 用标准库 zlib，不需要 brotli 之外的东西。
3. **多格式输出时**（F3.11），CSS 按优先级排列 `format()` 提示，浏览器自动取第一个支持的：

```css
src: url("fonts/MyFont-0.woff2") format("woff2"),
     url("fonts/MyFont-0.woff")  format("woff");
```

### 6.9 策略预设（F2.10）

把「每片多大」收敛为三个**目标导向**档位，界面默认只露出这三档 + 一个「每片字数」旋钮（手动改过即自动切为「自定义」）。三档只决定固定的每片字数，其余字段（兜底 / ASCII 首屏片 / ASCII 保底）保持原样。

| 档位 | 口径 | 每片字数 |
|---|---|---|
| **细切 fine** | 片数多、首屏命中更精细，代价是请求数偏多 | 1500 |
| **中切 medium** | 片数与体积折中（默认，全量约 2 万字时 ~13 片） | 4000 |
| **粗切 coarse** | @font-face 数量最少，代价是单页加载字节更多 | 8000 |

实现于 `src/core/presets.ts`（`applyPreset` / `detectPreset` / `estimatePreset`），界面在 `StrategyPanel` 展示。

### 7.1 形态决策

采用**本地 Web 服务**：Vite + React 前端 + Node API 服务 + Python 字体处理子进程。

选型依据（完整的三方案评估见附录 A）：

- 字体处理必须跑原生进程。纯前端 WASM 方案受 32 位地址空间限制（堆上限约 2GB，且**只增不减**），10MB 字体峰值已达 ~1GB，批处理多字重时必然 OOM
- 本地服务开发调试最快，且保留了演进为云端服务的可能
- 相比 Tauri，绕开了「把 Python fonttools 打进 app bundle」这个麻烦环节，也不需要 Xcode / Rust 工具链与签名公证

  options: {
    format: OutputFormat[];   // F3.10 默认 woff2；F3.11 支持多选
    fontDisplay: 'swap' | 'block' | 'fallback' | 'optional';

export interface JobResult {

    fontName: string;
    weight: number;

      charCount: number;

### 7.4 两阶段子集化（F3.8，性能优化）

**问题**：`pyftsubset` 每次调用都要重新解析整个源字体。10MB 字体解析约 5–10s。7 字重 × 20 分片 = 140 次调用 = 重复解析 140 次。

**方案**：

```
阶段一：源字体 (12MB) --pyftsubset--> 中间 TTF (含全部 3000 目标字符，约 1MB)
阶段二：中间 TTF --×20--> 20 个分片 woff2（每次解析 1MB，极快）
```

解析成本从「140 × 重」降为「7 × 重 + 140 × 轻」。

注意：阶段一必须保留全部布局特性（`--layout-features=*`），否则阶段二无法还原。且阶段二输出的 woff2 仍需复用阶段一的 cmap/GSUB/GPOS 语义。

**v1 已实现两阶段（见 `engine/subset.py`）：阶段一并集子集化得中间字体，阶段二逐片轻量子集化并转格式，比单阶段显著更快。**

## 8. A 方案（Tauri）扩展设计

v1 只做接口定义与目录预留，不实现。但架构必须保证后续改造成本可控。

### 8.1 隔离点

UI 层只依赖 `EngineClient` 接口（§7.3），不感知传输方式。

```
C 方案：web/ → httpAdapter  → fetch(/api)  → Node server → Python
A 方案：web/ → tauriAdapter → invoke(cmd)  → Rust sidecar → Python
```

改造工作量：**新增 `tauriAdapter.ts` + Rust 侧 command 桥接，UI 零改动。**

### 8.2 需要额外解决的三件事

| 事项 | 说明 | 预估难度 |
|---|---|---|
| **Python 依赖分发** | 不能要求终端用户装 Python。方案：PyInstaller 打包 fonttools 为独立二进制（约 30–40MB），或改用 Rust 原生子集化库 | 高 |
| **Sidecar 打包** | Tauri externalBin 配置、路径解析、进程生命周期 | 中 |
| **签名与公证** | macOS 需 Developer ID 签名 + notarization，否则 Gatekeeper 拦截 | 中 |
| **Rust 工具链** | 需 Xcode Command Line Tools + Rust，构建时间显著变长 | 中 |

### 8.3 触发时机

满足以下任一条件时启动 A 方案改造：

- 需要分发给不懂命令行的设计师 / 客户
- 用户反馈「装 Python 太麻烦」成为主要流失点
- 需要完全离线的一键安装包

在此之前保持 C 方案，把精力投入在拆分策略与预览体验上（这才是产品的真正难点）。

**字体文件体积的事实基线**（用于容量规划）：

- 单字重中文字体 TTF/OTF 集中在 **10–25MB**，物理上限约 40–60MB（CJK 全部码位约 9.8 万 × 每字形 200–500 字节）
- woff2 约为 TTF 的 40–60%
- **「几百 MB」通常不是单个文件，而是多字重家族压缩包**（7 字重 × 15MB ≈ 100MB）。因此核心需求是**批处理**，不是超大单文件处理
- 输入若为 woff2，需先 Brotli 解码重建 glyf，内存峰值比同内容 TTF 更高
